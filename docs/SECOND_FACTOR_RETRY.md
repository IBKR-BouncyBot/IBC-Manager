# Second-factor retry in 2.0.2

Engine revision: 3.24.2-manager.3. Upstream snapshot: IBC 3.24.2.

## Local contract

Enabled profile retry generates `ReloginAfterSecondFactorAuthenticationTimeout=yes`
and `SecondFactorAuthenticationTimeout=300`. A one-shot monotonic timer begins when
this engine observes a second-factor challenge. Duplicate events do not postpone
it; natural closure does not trigger early login or cancel the existing deadline.
There is no Android/iOS notification-dismissal event connected to Manager.

At expiry, pending authentication, generation, provider, credentials and shutdown
state are rechecked. If the challenge is still visible, only its one recognized,
visible and enabled Cancel button may be invoked. The engine then allows up to
ten seconds for a usable registered login form. All Swing mutation happens on the
Gateway JVM's event thread; there is no Robot/global focus automation.

## Defects reproduced against 2.0.1

1. A cleared password can keep Log In disabled. The old adapter waited for enabled
   Log In before invoking the handler that fills the password. The regression
   fixture failed with the old code and passed after separating preparation/submission.
2. The old adapter captured one JFrame and rejected a reconstructed login frame.
   The login handler also filtered its WINDOW_OPENED event while 2FA was pending.
   The new handler registers the recognized replacement without immediate submission;
   it stays bound to the same provider/challenge generation and original deadline.
3. Inline 2FA observation used to require an initial literal LOGIN heading. The
   observer now looks for the actual SECOND FACTOR AUTHENTICATION transition after
   live login even when that earlier heading was absent.
4. Re-entering the normal full handler after preparation can write fields a second
   time and disable the button during asynchronous validation. The retry now uses
   a prepared-submit path that retains pre-login checks but does not re-fill fields.

The adapter prepares credentials once per registered frame and field identities,
then waits for Gateway's actual button enabled state. Multiple recognized login
frames, competing modal dialogs, missing selectors, missing credentials and disabled
fields remain blocked. The engine never selects a new arbitrary desktop window.

A hidden retained SECOND FACTOR AUTHENTICATION label is not considered an active
challenge. Heading detection now requires a showing Swing label; an already restored
inline login form therefore does not require another Cancel action.

## Failure evidence and limits

The submitted incident ZIP was generated by Manager 1.0.22 on 2026-10-07, before
these integrated timers existed. It cannot identify the precise path in the user's
new 2.0.1 test. Source/fixture repair is proven for the cases above; actual receipt
of a fresh phone prompt is not established by synthetic Swing controls.

The log reports ARMED, DUE, STARTED and BLOCKED; STARTED means local login initiation,
not server acceptance or notification delivery. Blocked messages distinguish missing
stored credentials/frame, competing modal, unresolved cancellation, unsupported form
and a button that remains disabled after restoration. They carry no credential values.

Success, explicit failed-login state, Stop, changed provider or a superseding challenge
invalidates old callbacks. Approval concurrent with cancellation cannot be an atomic
transaction with the remote server; approval may be needed again on a replacement
request. There is no TOTP, approval bypass, process kill or unbounded rapid login loop.
A frozen Swing event thread is outside this timer's recovery capability.

The unused SecondFactorAuthenticationExitInterval and wrapper-timeout dropdown are
not configurable in the current Profile. The existing wrapper's reserved exit-code
handling is retained; the current retry path does not generate that exit code.

## Windows acceptance

Use the new application and engine, with a stored password and retry enabled. Leave
one real notification unanswered, then separately test dismissing it without approval.
Check the local challenge/due/credential/login sequence and phone receipt separately.
Also test early approval, a naturally expired prompt, disabled retry and Stop before
the deadline. A paper login without 2FA cannot validate this path. Export a new
Diagnostics ZIP immediately after a failure; include the visible Gateway login/prompt
screenshot without secrets. Do not rely on the old October 7 archive for this test.
